# Changelog — January 2026

## 2026-01-31 — Investment Planning API Compatibility Fix

### Summary
Fixed Go backend investment planning API to be fully compatible with the www_v1 API contract. The client was sending www_v1 format, but Go expected different field names and structure, causing validation errors and 404s.

### Root Cause
Schema mismatch between client and Go backend:
| Client Sends | Go Expected | Issue |
|--------------|-------------|-------|
| `availableCapital` | `budget` | Field name mismatch |
| `financialAssumptions.downPaymentPercent` | `downPaymentPercent` (flat) | Nested vs flat |
| `constraints.riskTolerance` | `riskTolerance` (required) | Nested vs flat + required |
| `cacheKey` | Not supported | Missing field |

### Changes Made

**1. Updated `InvestmentPlanningRequest` Struct**
- Added nested structs: `FinancialAssumptions`, `InvestmentConstraints`, `MarketFilters`
- Changed `Budget` → `AvailableCapital`
- Moved `DownPaymentPercent` into `FinancialAssumptions` (optional, default 20%)
- Moved `RiskTolerance` into optional `Constraints` (default "moderate")
- Added new fields: `CacheKey`, `TargetPropertyValue`, `RecommendedZipCodes`, `ExpansionRadius`, `IncludeAllTowns`, `ForceRefresh`, `SearchFilters`, `MarketFilters`

**2. Updated `QueueInvestmentPlan` Handler**
- Extracts nested fields with sensible defaults
- Added cache check before creating new jobs (returns cached result immediately)
- Updated response to include `responseKey` and `status` fields
- Passes all optional fields to job payload

**3. Fixed Delete Handler**
- Now deletes from both plain key format (www_v1) and legacy `cache:{userId}:{key}` format
- Fixed SQL LIKE pattern bug: `investment_plan:%` → `investment_plan_%` (colon → underscore)

**4. Fixed Get Handler**
- Added `responseKey` field to response for consistency with www_v1

**5. Added Compliance Filtering (ADR-051)**
- Filter `recommendations` array through SEC compliance filter
- Filter `riskAnalysis.warnings` through compliance filter
- Uses existing `compliance.Filter` from `internal/services/ai/compliance/`

**6. Added Dynamic SSE Timeout**
- Calculates timeout based on location count: 5 minutes base + 30 seconds per location
- Prevents premature timeout for multi-location plans

**7. Fixed Worker Cache Key Format**
- Worker was creating compound keys `investment_plan:{userId}:{cacheKey}`
- Changed to use client-provided `cacheKey` directly (matches www_v1)

### Files Modified
| File | Changes |
|------|---------|
| `internal/api/handlers/ai/handler.go` | Struct updates, handler fixes, compliance filtering, SQL LIKE fix |
| `internal/services/jobs/workers/investment_planning.go` | Fixed cache key format to match www_v1 |

## 2026-01-30 — Config Loading Fix + Reset Search Cache Invalidation

### Summary
Fixed Viper config loading bug that prevented `.env.local` from being read properly, causing `WRITE_TIMEOUT=60s` to be ignored. Also added property search cache invalidation when user clicks "Reset Search" in the client.

### Config Loading Bug Fix
**Problem**: `WRITE_TIMEOUT=60s` in `.env.local` was being ignored, causing I/O timeout at ~35 seconds (server used default 30s).

**Root Cause**: `v.SetConfigName(".env.local")` with `SetConfigType("env")` makes Viper look for `.env.local.env`, not `.env.local`.

**Fix**: Use `v.SetConfigFile(".env.local")` instead, which takes the exact filename.

**Files Modified**:
- `internal/config/config.go` - Fixed `.env.local` loading with `SetConfigFile()`, added timeout logging

### Reset Search Cache Invalidation
When user clicks "Reset Search" in the client, server-side cache (Redis + PostgreSQL) is now cleared for that location, ensuring fresh data on next search.

**Server-Side**:
- `HybridCache.DeleteByKeyPattern()` - New method for pattern-based cache deletion
- `Orchestrator.InvalidateCache()` - Now actually deletes cache (was a stub)
- `Orchestrator.InvalidateCacheByKey()` - New method for specific key deletion
- `POST /api/v2/discover/cache/invalidate` - New endpoint for cache invalidation

**Client-Side**:
- `invalidatePropertySearchCache()` - New API function
- `handleClearResults()` - Now calls cache invalidation API before clearing local state

**Files Modified**:
- `internal/services/cache/hybrid.go` - Added `DeleteByKeyPattern()` method
- `internal/services/property/finder/orchestrator.go` - Implemented `InvalidateCache()`, added `InvalidateCacheByKey()`
- `internal/api/handlers/discover/enrichment_sse.go` - Added `InvalidateSearchCache` handler

- `client/src/lib/api/client.ts` - Added `invalidatePropertySearchCache()`

## 2026-01-30 — Async Enrichment with SSE + Timeout Fixes

### Summary
Added async enrichment mode using Server-Sent Events (SSE) so property search returns immediately while enrichment happens in background. Also fixed client/server timeouts.

### Timeout Fixes
- **Client**: Added 90-second timeout to all API requests using `AbortController`
- **Server**: `WRITE_TIMEOUT=60s` now properly applied (was defaulting to 30s causing I/O timeout errors)
- **Root cause**: I/O timeout at ~35 seconds was server's default 30s WriteTimeout, not client-side

**Files Modified**:
- `client/src/lib/api/client.ts` - Added 90s timeout to `apiFetch`, `downloadDecisionRecord`, `exportBatchEvaluation`

### Async Enrichment (Option A Implementation)
Properties are returned immediately after search. YearBuilt/sqft/lotSize/rentEstimate enrichment happens in background via HasData Property API.

**Server-Side**:
- `SearchAsync()` method in orchestrator returns immediately with `enrichmentJobId`
- `EnrichmentJobManager` handles background enrichment with worker pool
- SSE endpoint streams real-time updates: `/api/v2/discover/enrich/{jobId}/stream`
- Polling endpoint for status: `/api/v2/discover/enrich/{jobId}`

**Client-Side**:
- `SearchResponse` now includes `enrichmentJobId` and `enrichmentStatus`
- `subscribeToEnrichmentUpdates()` - SSE subscription helper
- `getEnrichmentStatus()` - Polling fallback
- Types: `EnrichmentJobStatus`, `EnrichmentUpdate`, `EnrichmentStatus`

**Files Modified**:
- `internal/services/property/finder/orchestrator.go` - Added `SearchAsync()`, `GetEnrichmentJobManager()`
- `internal/services/property/finder/enrichment_job.go` - New file: job manager with worker pool
- `internal/api/handlers/discover/enrichment_sse.go` - New file: SSE streaming + polling handlers
- `internal/api/handlers/discover/handler.go` - Initialize enrichment job manager
- `internal/api/router.go` - Added `/enrich/{jobId}` and `/enrich/{jobId}/stream` routes
- `client/src/lib/api/client.ts` - Added enrichment types and SSE subscription

### Usage

**Server** (already integrated):
```go
// Use SearchAsync for immediate response + background enrichment
response, err := orchestrator.SearchAsync(ctx, params)
// response.EnrichmentJobID can be used by client for SSE
```

**Client**:
```typescript
import { searchProperties, subscribeToEnrichmentUpdates } from '@/lib/api/client';

const result = await searchProperties(criteria);

if (result.enrichmentJobId && result.enrichmentStatus !== 'COMPLETED') {
  const { unsubscribe } = subscribeToEnrichmentUpdates(result.enrichmentJobId, {
    onUpdate: (update) => {
      // Update individual property in state
      updateProperty(update.propertyIndex, update);
    },
    onComplete: (status) => {
      console.log(`Enrichment complete: ${status.enriched}/${status.total}`);
    },
  });

  // Cleanup on unmount
  return () => unsubscribe();
}
```

## 2026-01-30 — Property API Response Structure Fix

### Summary
Fixed HasData Property API response parsing. The API returns property data nested under a `property` field, not at the top level.

### Bug
All 41 property enrichment calls were returning zero values (enriched: 0) because the Go struct expected fields at top level:
```go
// WRONG - expected fields at top level
type hasDataPropertyAPIResponse struct {
    RequestMetadata ...
    YearBuilt       int  // Not here!
}
```

### Fix
Updated struct to match actual API response with nested `property` field:
```go
// CORRECT - matches actual API response
type hasDataPropertyAPIResponse struct {
    RequestMetadata hasDataRequestMetadata     `json:"requestMetadata"`
    Property        hasDataPropertyAPIProperty `json:"property"`
}

type hasDataPropertyAPIProperty struct {
    YearBuilt     int `json:"yearBuilt"`
    LivingArea    int `json:"livingArea"`
    LotSize       int `json:"lotSize"`
    RentZestimate int `json:"rentZestimate"`
}
```

### Files Modified
- `internal/services/property/providers/hasdata.go` - Fixed response struct nesting
